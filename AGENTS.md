# Mission Relay contributor instructions

For an existing-chat continuation, a newly matching latest user prompt is not
proof that the visible assistant belongs to that prompt. ChatGPT can re-render
the prior assistant while the new response is pending. Compare candidates with
the **durably verified previous assistant SHA-256** (not only a transient
post-click DOM baseline); never credit unchanged prior bytes unless a distinct,
non-fallback assistant message identity proves an intentional identical reply.
Keep the original one-Send reservation, timeout and fail-closed semantics.
Previously misattributed production rounds require separate, append-only,
independently evidenced correction; a source fix does not repair old SQLite.
The local `browser-correct-attribution` recovery requires the pinned original
ChatGPT tab, unchanged latest reserved user SHA-256, two stable complete
assistant reads and an exact new full-answer SHA-256. It preserves the false
observation and original PI decision, appends a one-shot correction without a
new browser Send/round and locks subsequent dispatch until PI independently
reviews the corrected answer. `pi-evidence` must report the original and
effective hashes, all correction event IDs, and an unreviewed correction as
inconsistent. Adjacent identical answer hashes are only *suspect*, not proof
of misattribution: a distinct assistant message can legitimately be identical.
Never fabricate evidence or clear old error records to bypass this process.

Read-only PI health/evidence and Telegram status may expose a **new-conversation reservation intent** flag from private SQLite. It must be false for same-chat and settled requests and must never be treated as proof of a new tab, submitted Send, observed URL or completed response. Never recover, replay or deploy based on this flag alone.

Side-effect-free browser reads used before a PI recovery or Send reservation have a 30-second deadline. An expired read can interrupt PI safely without reserving or retrying a browser Send; a late-created Playwriter connector is closed. Never wrap an actual Send, Retry, reservation or PI decision in that timeout: an external side effect may already have committed.

This is an independent, public, local-first open-source project. It does not depend on any private AIOS deployment.

## Boundaries
- PI planning/control rules belong in the PI planner prompt, not in ChatGPT executor messages. ChatGPT browser prompts are direct task imperatives with scoped permissions and checkable evidence, without third-person owner-authorization boilerplate. Explicit `【执行与自治规则】` coordinator-only sections and exact redundant third-person owner-authorization lines in the saved full owner goal are omitted deterministically from executor prompts (not from PI decisions or SQLite records). Keep exact prompt reconstruction for recovery intact.
- Telegram `/list` is an actionable inbox, `/history` is an audit-oriented history view; local `archive-settled` marks only safely settled Missions without deleting SQLite records or events. Never hide NEEDS_RECONCILIATION, reserved/uncertain Sends or pending PI checkpoints. Inline callback buttons are read-only, owner/private-chat verified and deduplicated through the existing command inbox.
- A `pi.autopilot_finished` event can mean `LIMIT`, not business DONE: it is emitted at the 32-turn budget boundary before or while a successor Mission is created. Never classify such a PI `NEXT/HANDOFF` checkpoint as settled solely due to that event, even if a READY child already exists. Only the durable latest PI `DONE/BLOCKED` verdict is terminal for archiving a PAUSED PI Mission. Do not clear or reverse older archive metadata without a separate evidenced repair.
- Mission Relay owns mission policy, state transitions, recovery and evidence. Agents execute; they do not declare themselves verified.
- Official SDKs are execution adapters, not sources of mission truth.
- A mission has exactly one authoritative provider and one active writer. Never silently retry an ambiguous external side effect.
- Native CLI and SQLite state management are implemented. Telegram remains an opt-in foreground channel; Playwriter is an experimental opt-in browser adapter with verified real post-fix Telegram → existing Chrome ChatGPT → durable final-answer receipt, two consecutive real CLI-driven browser turns, relay restart/reconnect and conservative no-replay reconciliation of an interrupted send. ChatGPT DOM virtualized-count recovery and user-controlled revoke/re-enable of the exact approved tab both passed live readback, with unchanged SQLite receipt and no replay. Browser Mission/lock reconciliation is one atomic SQLite transaction in current source; preserve support for recovery of earlier partially reconciled records. Arbitrary remote browser gestures, browser-wide permission-scope tests and unattended operation remain unverified. PWA remains unimplemented.
- The opt-in Playwriter experiment may read visible ChatGPT conversation elements and use its normal composer only after the user has enabled the extension on the exact tab. Do not access cookies, private tokens, internal ChatGPT APIs or other tabs. Selectors are fallible; fail closed when the UI is unrecognized.
- Never commit secrets, private task records, browser profiles, local state databases, workspace outputs or user-identifying configuration.
- Optional Windows Telegram task lifecycle is operator-enrolled, interactive-user only, and uses user-bound DPAPI credentials outside the checkout. It must not install or start on build. Never run both the foreground and task pollers. Restart only when no in-flight Mission, queued Telegram delivery, or reserved browser Send is observed; the idle gate is not an atomic drain. Playwriter relay remains independently managed.
- Telegram `channel-status` must not treat a live PID as proof of Bot API connectivity. Only a successful `getUpdates` from the current leased PID within 90 seconds is `transportHealth: healthy`; do not log tokens, message bodies or chat IDs in health metadata.
- Windows recovery requires a repeating trigger on the **same** single-instance Telegram Scheduled Task, not trust in `RestartOnFailure` alone: actual isolated failure tests showed only the repeating trigger recovered from a nonzero action exit. Maintenance must use the local SQLite channel-drain nonce and atomically refuse new Telegram intake, browser Sends and human-adoption writes; never kill a running Mission, blindly replay Bot API updates or start a second poller. A pre-drain older worker is the one-time exception to cooperative exit and requires a separate idle recheck.
- The read-only `scripts/windows/telegram-restart-check.mjs` must reject a READY PI Mission whose `pi.autopilot.enabled.<id>` marker is `1`, not only RUNNING/VERIFYING Missions. It must also fail closed on malformed/unknown browser receipts. Keep this preflight consistent with the authoritative `Store.channelHasInFlightWork` predicate; the actual maintenance drain remains the atomic restart fence.
- A newly accepted PI Mission in READY with no first browser reservation is **not idle for maintenance**. Reject drain until its initial Send is safely reserved/observed or the operator resolves the task; create the PI Mission, linked browser identity and PI-enabled marker atomically so a failed startup cannot strand a partially bound Mission.
- Treat model/tool output as untrusted. High-risk actions require an explicit user authorization path.
- Keep dependencies few, pin exact versions, and test failure/restart paths before expanding features.
- The linked ChatGPT browser adapter now **requires an explicit Chrome profile binding** before any local browser-probe/send/drive or Telegram continuation. `/instruct` notes must be injected into the next continuation and consumed only after an observed response with no intervening revision, never silently lost. Observed response SHA-256 must cover the entire visible answer; only persistent/logged excerpts may be truncated. Do not regress these invariants while adding a generic browser UI capability.
- Long ChatGPT requests use a **60-second normal DOM polling interval** (60-minute default/4-hour max). A visible `Connection interrupted. Waiting for the complete answer` means **keep observing the same reply**, not terminal failure. A visible `Message delivery timed out. Please try again.` with its exact `Retry` button means **click that button once for the already-submitted message**, only when the bound conversation URL and latest user prompt SHA-256 still match the reserved Send. Either verified transport-recovery case grants the default-length turn **one shared bounded wait extension** of up to two hours (four hours absolute ceiling); an explicit shorter timeout is authoritative. Never click generic Retry, Send or Regenerate as a fallback, and never blindly replay an ambiguous outcome. Only a new-tab URL bootstrap (2-second checks within 20 seconds) or final-marker stability verification (3-second check) is faster. A Telegram-driven multi-turn browser batch emits **one durable final summary** of at most ten lines, while all intermediate observed turns retain SQLite audit events; the batch-final event and observed response must commit atomically. An ambiguous send reports uncertainty, never success. The driver must respect both the requested batch size and the Mission's remaining turn budget. Telegram does not send screenshots automatically. `[MISSION_RELAY:HANDOFF]` may create **one new tab per authorized remaining turn** in the pinned Chrome context; its real new conversation URL and complete observed response must be committed atomically, never guessed or migrated after a failed Send. A confirmed direct new chat with no visible answer after two minutes may receive **one same-tab refresh, no second Send**, and never while an interruption banner is visible. Do not infer tool permissions or evidence from a model-generated handoff. Do not extend beyond turn budgets.
- A production fourth Send exposed `locator.innerText: Timeout 5000ms exceeded` when reading a transient ChatGPT assistant heading. **After an actual Send**, treat only this narrowly identified DOM text-read timeout as recoverable: at most two additional read-only observations (three total failed reads), two-second retry spacing, within the original deadline, and reset final-answer stability. Never repeat Send or UI Retry for this DOM error. All other exceptions, three consecutive failures, and inaccessible exact original conversations remain uncertain; no fabricated recovery. Apply this to both existing-chat and new-chat Send observation loops.
- A stale `This response couldn’t load` visible *before* sending is not proof the newly sent request failed. Attribute new error observations to the exact latest user prompt and an actual changed assistant turn, never just a time window. `browser-recover-turn` may credit an uncertain original-conversation request only after read-only exact-prompt and stable-response verification plus explicit operator side-effect acknowledgement; retain the original uncertainty audit, original request key and no-replay invariant. A recovered model `DONE` does not equal independently verified business completion.
- A production Chrome watch + PI test exposed that a later owner/PI message may quote the entire earlier user prompt. **Never use substring containment to attribute a generated answer to a pending ChatGPT Send or recovery receipt.** Compare the latest visible canonical user prompt SHA-256 with the exact submitted prompt SHA-256 for normal existing/new-tab observations and both `browser-recover-*` paths. Preserve the at-most-once reservation and fail closed if the latest user has changed.

## Development

- The single Telegram process may voluntarily exit after five minutes without loop progress only with its current SQLite lease and no active Missions, reserved browser Sends, undelivered commands/notifications or drain; the existing Windows repeating Task restarts it. Never start another watchdog daemon or auto-kill an active/ambiguous browser operation. A blocked JS event loop cannot self-recover.
- Record a sanctioned voluntary idle-stall code-75 exit into the existing private SQLite metadata before terminating, with only UTC timestamp, PID, elapsed idle time and exit code. `channel-status.lastIdleExit` is diagnostic history, not proof of the cause of an unrelated exit. Never expose bot tokens, chat IDs, message text or full browser URLs in watchdog metadata.
- An explicitly interrupted PAUSED PI Mission with no reserved or uncertain Send must not monopolize the owner new-task route. Preserve its original error, audit and request identity without auto-replay. Unresolved Sends and unreviewed complete responses remain blockers.

- For the owner deployment, maintain and commit source from the durable AIOS Linux project checkout. GitHub `main` is the promotion boundary; GMK's Windows clone is a pull-only runtime deployment. Do not develop independent competing GMK commits or synchronize private SQLite, DPAPI credentials or browser profiles across machines. Use the existing Windows drain/task for controlled activation after Linux and cross-platform checks; see `docs/operations.md`.
- A recovered browser turn can be a valid PI checkpoint only with its exact original request key, complete answer SHA-256 and independently inspected recovery event. A manual side-effect acknowledgement without an observed answer is not a PI checkpoint. Neither case permits blind Send replay.
- The read-only `pi-health` CLI and authenticated Telegram `/status` expose only bounded request/PI status, timestamps, observed turns and whether a full answer hash exists. They must not expose actual prompt/answer text, owner directives, request keys, Chrome IDs, private ChatGPT URLs or tokens. Keep PI liveness and Telegram transport health separate: an old `reserved` receipt is never proof that a model has stalled, and a healthy Bot API poll is never proof of browser progress. Prioritize active/uncertain work over old paused checkpoints in bounded diagnostics; never add a new poller for health checks.
- The read-only `pi-evidence <mission-id>` CLI must build its verdict solely from existing append-only receipt events, PI decisions and persisted bounds, without opening Chrome or creating any tool side effects. Verify answer-to-decision SHA, sequential rounds, unique reservations and a maximum of five observed sends per conversation. Recovered browser replies count only when independently inspected. Report missing PI review rather than inventing one. The JSON may include response SHA-256 and event IDs for audit, never raw answers/prompts, request keys, browser links, model-generated evidence claims or approval secrets. Even a consistent ledger is never independent acceptance of source changes or v1.0.
- For a normal `chatgpt.browser_migrated` event, independently verify an existing unused reservation request key, two different valid URL SHA-256 values, and the next observed reply's exact same request key; orphan, duplicated, incorrectly attributed or invalid-URL migration events must make `pi-evidence.ledgerConsistent=false`. Independently recovered rollovers use their own one-shot event with independently inspected evidence; never accept a fabricated migration as a reset of the five-Send ceiling.
- The independent migration audit must also verify URL-hash **continuity across successive chats**: after the first recorded destination, each normal or independently recovered next-chat event must have a source hash equal to that previously observed destination. A syntactically distinct but unrelated source URL must not reset the five-Send ceiling or make a 5→6 acceptance look valid. Keep only hashes in the report; the very first adopted/linked source URL has no earlier migration event and is not independently reconstructable from the ledger.
- `pi-chain-evidence <mission-id>` is a bounded (64-Mission maximum), read-only lineage audit, not an autonomous chain launcher. Require reciprocal parent/child records and audit events, original owner scope and browser binding, exact 32-turn PI NEXT/HANDOFF/LIMIT answer hashes, and a new ChatGPT conversation on the successor's **first** Send. A later migration must never erase evidence of an invalid first child Send. Multiple identical base PI decisions on one round are invalid; legitimate later PI revisions may be recorded, but the original and all revisions must agree with the observed full answer SHA. Do not substitute this event audit for live business acceptance.
- All three standalone PI diagnostic CLIs (`pi-health`, `pi-evidence`, `pi-chain-evidence`) must open SQLite with read-only file flags and `PRAGMA query_only`, without creating a state directory, executing migrations, or acquiring any writer role. Missing databases and schema versions other than current v3 fail closed. The normal Telegram controller and mutating CLI commands keep the existing writable `Store` behavior. Never treat an ambiguous browser Send as an observed response or reset its original request just to enable deployment.

- Telegram ordinary text and `/new` create one new read-only ChatGPT conversation only via a local, previously approved exact Playwriter anchor tab. `/agent` requires a locally approved read-only workspace and a separately installed native executor plugin, whose authentication and tool permissions must be verified by that plugin. Preserve fail-closed authorization, at-most-once browser sends, request-key persistence, single final Telegram notifications and local revocation; neither pathway authorizes generic browser gestures, writes or implicit provider switching.
- Owner-authenticated Telegram ordinary text, `ChatGPT:` and `/auto` now use a bounded PI-coordinated ChatGPT browser workflow; `/new` remains the old one-turn no-PI route. PI runs on an explicitly configured remote SSH/pictl route with **no model tools** and cannot authorize new permissions. Each observed ChatGPT reply and full SHA precedes PI inference; queued owner notes are durably reviewed before the next Send, and PI NEXT/DONE/BLOCKED/HANDOFF decisions are checked and recorded. Never trust ChatGPT's flow marker to declare PI acceptance. A paused crash checkpoint may resume only after the exact latest user prompt and assistant answer hashes match the durable observed receipt. A reserved, uncertain, changed or unavailable ChatGPT turn MUST NOT be replayed. Keep the old Codex route optional and independent.
- PI Telegram tasks use a bounded 32-send Mission and must switch ChatGPT conversation after at most five observed Relay sends in the same chat (or earlier PI HANDOFF), counting only durable receipts across recovery. At the 32-turn boundary, only a verified PI NEXT/HANDOFF may produce an atomically created, single successor Mission (same scope and owner goal, distinct request key and freshly verified parent answer before its first new-tab Send). On restart the controller recreates a missing child idempotently; no ambiguous Send may be replayed. A newly created READY successor may receive owner notes before its first Send: PI must review these against the exact parent response, commit the revised child plan and directive acknowledgements atomically, and reconstruct that exact child plan for uncertain new-tab recovery. If notes race the final SQLite reservation, reject the stale prompt and retry only planning without a Send. Revoked `/build` approval must also be checked atomically at reservation time, not merely before PI inference. Emergency `/pause` on an ancestor must stop its READY/RUNNING descendants from new Sends after the current in-flight response. PI gets up to 100,000 characters of the visible assistant answer, including its middle; Telegram still gets an abbreviated report. A one-turn PI DONE is valid when the owner's actual goal is satisfied; never force extra turns just to meet a test count. A separately approved /build route provides a ChatGPT prompt-level workspace-write path. Synthetic cross-Mission tests are not unattended production acceptance.
- The five-Send chat ceiling is also an **atomic SQLite reservation invariant**, not just a PI/browser-drive preflight: `reserveChatBrowserTurn` rejects a sixth same-chat request before creating a request key or touching Chrome. Only `executeBrowserRollover` reserves with `newConversation:true`; it must commit an independently observed **distinct direct** ChatGPT URL together with the response before that Send is credited. A failed rollover remains uncertain with the original request identity; never make it a same-chat Send to work around the guard. Keep the existing independent ledger checks for historical malformed records.
- On PI `NEXT`/`HANDOFF` chat rotation, including automatic 5→6, pass the last durable source user-prompt and full-answer SHA-256 values to `executeBrowserRollover.expectedSource`. Its read-only DOM check must reverify both immediately before SQLite reservation, even if `drivePiAutopilot` already checked the page earlier. A changed source must produce no reserved request, new tab or Send. This is a deterministic race guard, not evidence that 5→6 has passed live Chrome acceptance.
- The same final source correlation is mandatory for ordinary **same-chat PI NEXT**, not only rollover: `executeBrowserTurn.expectedSource` rechecks the complete assistant answer and latest canonical user prompt against durable receipt hashes after PI's earlier preflight and before SQLite Send reservation. Multi-turn manual browser-drive must pass the corresponding receipt hashes for each intra-batch NEXT/HANDOFF. Any changed source refuses dispatch without a reserved request or browser Send; do not weaken this gate to address a missing tab or stale model answer. Synthetic source-change tests are not live browser acceptance.
- The first Send of a 32-turn PI successor additionally requires `newConversation:true` in the same atomic reservation. Recheck the parent still has an unpaused, error-free, verified LIMIT/NEXT or HANDOFF checkpoint and reciprocal child relationship before reserving. This is an enforcement boundary; historical ledger tests may inject deliberately malformed records in isolated test databases but never bypass the production gate. Do not interpret a new-tab reservation flag as evidence of a real migrated URL.
- An authenticated Telegram `/build` command can create a PI-managed workspace-write Mission only when the local operator has pinned `telegram-build-project` to the exact configured PI project path. The recorded scope must propagate to PI and ChatGPT on every turn, including HANDOFF. PI stays tool-free; ChatGPT must actually have connected execution tools. Read-only `/auto`, native `/agent` and legacy `/continue` never inherit this authorization. Local approval revocation prevents subsequent sends; this is browser prompt authority, not an OS-enforced sandbox. For cross-Mission first-new-tab sends, recheck the exact parent visible prompt/answer SHA again immediately before SQLite reservation, after any asynchronous PI preflight; refuse a changed parent without Send. Do not assert Git or deployed effects without real readback.
- Fresh Telegram ChatGPT task goals (`/build`, `/auto`, `/new` and plain ChatGPT tasks) allow up to **4000 characters** within Telegram's 4096-character single-message transport limit. This is separate from the **1500-character** bound on PI `nextPrompt`, queued owner notes and `/instruct`. Keep full owner goals intact across Mission and Chat handoffs. The 12000-character browser prompt cap is still authoritative: deterministically shorten only the redundant previous-answer excerpt on a long-goal rollover; never silently truncate the owner goal, PI directive or approved workspace. Recovery must reconstruct the identical prompt SHA.
- Node.js LTS (24+), `npm ci`, `npm run check`, `npm test`, `npm run build`.
- Browser-first default: no native coding-agent SDK or vendor selection is required. Native executors are operator-installed, in-process trusted plugins; each native Mission is pinned to one installed executor identity. All vendor-specific authentication, sandbox, proxies and SDK logic belong outside `src/core` and `src/plugins/telegram.ts`.
- Existing human ChatGPT conversation adoption is distinct from a Relay Send. Its stable user/answer hashes are a zero-turn checkpoint. PI's next reply must be grounded in that checkpoint; do not infer any browser Send from an adoption event. Playwriter tab groups are cosmetic; the optional browser watcher is deliberately profile-scoped (not group-scoped), baselines historical tabs on enable, and discovers only new/changed Playwriter-enabled ChatGPT dialogs. Do not claim control of unenabled Chrome tabs or silently adopt other websites. Watch revocation stops future dispatches; never replay ambiguous sends.
- New authenticated Telegram `/build`, `/auto`, ordinary ChatGPT and `/new` tasks may bootstrap a **new owned Playwriter tab** in the *already approved exact Chrome profile* if the saved source conversation is no longer enabled. The bootstrap visits only the previously approved ChatGPT URL, verifies an idle composer, sends **nothing** to the source, and opens a separate fresh conversation via the existing at-most-once rollover; close only the owned bootstrap source afterwards. Never enable or seize existing inaccessible tabs, switch Chrome profiles, or use bootstrap for uncertain-Send recovery, adoption or continuation. If the pinned extension browser itself is disconnected, fail clearly without creating a Mission or Send. Preserve source/receipt hashes and all audit records.
- During a continuous PI or browser-drive loop, mark only the new tab returned by a **successfully observed and SQLite-committed** Relay rollover as disposable after a later verified rollover. Best-effort close the superseded Relay-owned tab only if it is distinct from the active destination and still at its exact expected old direct ChatGPT URL. Never close the caller's original/attached tab or an unproven tab from a previous process; failed/tab-hung cleanup cannot reverse a committed reply, replay a Send or block PI forever. Do not claim cleanup across restarts or separate manual invocations; real Chrome memory use is not proven by synthetic tests.
- Test with scripted fake executors; real Codex use is opt-in and requires an authorized account.
- Browser tests use a synthetic page unless the operator explicitly enables the Playwriter extension. Never run a real ChatGPT browser-send in CI or against an arbitrary open tab.
- Never run integration tests against a production repo or publish/restart services as a side effect.
- Update architecture/operations docs for protocol or state changes. Run `git status` and secret checks before public push.
- Read `STATE.md` before continuing implementation; it separates tested features from planned ones and tracks the current live-Codex blocker.
