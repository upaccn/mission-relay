# Mission Relay contributor instructions

This is an independent, public, local-first open-source project. It does not depend on any private AIOS deployment.

## Boundaries
- Mission Relay owns mission policy, state transitions, recovery and evidence. Agents execute; they do not declare themselves verified.
- Official SDKs are execution adapters, not sources of mission truth.
- A mission has exactly one authoritative provider and one active writer. Never silently retry an ambiguous external side effect.
- Native CLI and SQLite state management are implemented. Telegram remains an opt-in foreground channel; Playwriter is an experimental opt-in browser adapter with verified real post-fix Telegram → existing Chrome ChatGPT → durable final-answer receipt, two consecutive real CLI-driven browser turns, relay restart/reconnect and conservative no-replay reconciliation of an interrupted send. ChatGPT DOM virtualized-count recovery and user-controlled revoke/re-enable of the exact approved tab both passed live readback, with unchanged SQLite receipt and no replay. Browser Mission/lock reconciliation is one atomic SQLite transaction in current source; preserve support for recovery of earlier partially reconciled records. Arbitrary remote browser gestures, browser-wide permission-scope tests and unattended operation remain unverified. PWA remains unimplemented.
- The opt-in Playwriter experiment may read visible ChatGPT conversation elements and use its normal composer only after the user has enabled the extension on the exact tab. Do not access cookies, private tokens, internal ChatGPT APIs or other tabs. Selectors are fallible; fail closed when the UI is unrecognized.
- Never commit secrets, private task records, browser profiles, local state databases, workspace outputs or user-identifying configuration.
- Optional Windows Telegram task lifecycle is operator-enrolled, interactive-user only, and uses user-bound DPAPI credentials outside the checkout. It must not install or start on build. Never run both the foreground and task pollers. Restart only when no in-flight Mission, queued Telegram delivery, or reserved browser Send is observed; the idle gate is not an atomic drain. Playwriter relay remains independently managed.
- Telegram `channel-status` must not treat a live PID as proof of Bot API connectivity. Only a successful `getUpdates` from the current leased PID within 90 seconds is `transportHealth: healthy`; do not log tokens, message bodies or chat IDs in health metadata.
- Windows recovery requires a repeating trigger on the **same** single-instance Telegram Scheduled Task, not trust in `RestartOnFailure` alone: actual isolated failure tests showed only the repeating trigger recovered from a nonzero action exit. Maintenance must use the local SQLite channel-drain nonce and atomically refuse new Telegram intake, browser Sends and human-adoption writes; never kill a running Mission, blindly replay Bot API updates or start a second poller. A pre-drain older worker is the one-time exception to cooperative exit and requires a separate idle recheck.
- A newly accepted PI Mission in READY with no first browser reservation is **not idle for maintenance**. Reject drain until its initial Send is safely reserved/observed or the operator resolves the task; create the PI Mission, linked browser identity and PI-enabled marker atomically so a failed startup cannot strand a partially bound Mission.
- Treat model/tool output as untrusted. High-risk actions require an explicit user authorization path.
- Keep dependencies few, pin exact versions, and test failure/restart paths before expanding features.
- The linked ChatGPT browser adapter now **requires an explicit Chrome profile binding** before any local browser-probe/send/drive or Telegram continuation. `/instruct` notes must be injected into the next continuation and consumed only after an observed response with no intervening revision, never silently lost. Observed response SHA-256 must cover the entire visible answer; only persistent/logged excerpts may be truncated. Do not regress these invariants while adding a generic browser UI capability.
- Long ChatGPT requests use a **60-second normal DOM polling interval** (60-minute default/4-hour max). A visible `Connection interrupted. Waiting for the complete answer` means **keep observing the same reply**, not terminal failure. A visible `Message delivery timed out. Please try again.` with its exact `Retry` button means **click that button once for the already-submitted message**, only when the bound conversation URL and latest user prompt SHA-256 still match the reserved Send. Either verified transport-recovery case grants the default-length turn **one shared bounded wait extension** of up to two hours (four hours absolute ceiling); an explicit shorter timeout is authoritative. Never click generic Retry, Send or Regenerate as a fallback, and never blindly replay an ambiguous outcome. Only a new-tab URL bootstrap (2-second checks within 20 seconds) or final-marker stability verification (3-second check) is faster. A Telegram-driven multi-turn browser batch emits **one durable final summary** of at most ten lines, while all intermediate observed turns retain SQLite audit events; the batch-final event and observed response must commit atomically. An ambiguous send reports uncertainty, never success. The driver must respect both the requested batch size and the Mission's remaining turn budget. Telegram does not send screenshots automatically. `[MISSION_RELAY:HANDOFF]` may create **one new tab per authorized remaining turn** in the pinned Chrome context; its real new conversation URL and complete observed response must be committed atomically, never guessed or migrated after a failed Send. A confirmed direct new chat with no visible answer after two minutes may receive **one same-tab refresh, no second Send**, and never while an interruption banner is visible. Do not infer tool permissions or evidence from a model-generated handoff. Do not extend beyond turn budgets.
- A stale `This response couldn’t load` visible *before* sending is not proof the newly sent request failed. Attribute new error observations to the exact latest user prompt and an actual changed assistant turn, never just a time window. `browser-recover-turn` may credit an uncertain original-conversation request only after read-only exact-prompt and stable-response verification plus explicit operator side-effect acknowledgement; retain the original uncertainty audit, original request key and no-replay invariant. A recovered model `DONE` does not equal independently verified business completion.
- A production Chrome watch + PI test exposed that a later owner/PI message may quote the entire earlier user prompt. **Never use substring containment to attribute a generated answer to a pending ChatGPT Send or recovery receipt.** Compare the latest visible canonical user prompt SHA-256 with the exact submitted prompt SHA-256 for normal existing/new-tab observations and both `browser-recover-*` paths. Preserve the at-most-once reservation and fail closed if the latest user has changed.

## Development

- The single Telegram process may voluntarily exit after five minutes without loop progress only with its current SQLite lease and no active Missions, reserved browser Sends, undelivered commands/notifications or drain; the existing Windows repeating Task restarts it. Never start another watchdog daemon or auto-kill an active/ambiguous browser operation. A blocked JS event loop cannot self-recover.
- Record a sanctioned voluntary idle-stall code-75 exit into the existing private SQLite metadata before terminating, with only UTC timestamp, PID, elapsed idle time and exit code. `channel-status.lastIdleExit` is diagnostic history, not proof of the cause of an unrelated exit. Never expose bot tokens, chat IDs, message text or full browser URLs in watchdog metadata.
- An explicitly interrupted PAUSED PI Mission with no reserved or uncertain Send must not monopolize the owner new-task route. Preserve its original error, audit and request identity without auto-replay. Unresolved Sends and unreviewed complete responses remain blockers.

- For the owner deployment, maintain and commit source from the durable AIOS Linux project checkout. GitHub `main` is the promotion boundary; GMK's Windows clone is a pull-only runtime deployment. Do not develop independent competing GMK commits or synchronize private SQLite, DPAPI credentials or browser profiles across machines. Use the existing Windows drain/task for controlled activation after Linux and cross-platform checks; see `docs/operations.md`.
- A recovered browser turn can be a valid PI checkpoint only with its exact original request key, complete answer SHA-256 and independently inspected recovery event. A manual side-effect acknowledgement without an observed answer is not a PI checkpoint. Neither case permits blind Send replay.

- Telegram ordinary text and `/new` create one new read-only ChatGPT conversation only via a local, previously approved exact Playwriter anchor tab. `/agent` requires a locally approved read-only workspace and a separately installed native executor plugin, whose authentication and tool permissions must be verified by that plugin. Preserve fail-closed authorization, at-most-once browser sends, request-key persistence, single final Telegram notifications and local revocation; neither pathway authorizes generic browser gestures, writes or implicit provider switching.
- Owner-authenticated Telegram ordinary text, `ChatGPT:` and `/auto` now use a bounded PI-coordinated ChatGPT browser workflow; `/new` remains the old one-turn no-PI route. PI runs on an explicitly configured remote SSH/pictl route with **no model tools** and cannot authorize new permissions. Each observed ChatGPT reply and full SHA precedes PI inference; queued owner notes are durably reviewed before the next Send, and PI NEXT/DONE/BLOCKED/HANDOFF decisions are checked and recorded. Never trust ChatGPT's flow marker to declare PI acceptance. A paused crash checkpoint may resume only after the exact latest user prompt and assistant answer hashes match the durable observed receipt. A reserved, uncertain, changed or unavailable ChatGPT turn MUST NOT be replayed. Keep the old Codex route optional and independent.
- PI Telegram tasks use a bounded 32-send Mission and must switch ChatGPT conversation after at most eight observed Relay sends in the same chat (or earlier PI HANDOFF), counting only durable receipts across recovery. At the 32-turn boundary, only a verified PI NEXT/HANDOFF may produce an atomically created, single successor Mission (same scope and owner goal, distinct request key and freshly verified parent answer before its first new-tab Send). On restart the controller recreates a missing child idempotently; no ambiguous Send may be replayed. A newly created READY successor may receive owner notes before its first Send: PI must review these against the exact parent response, commit the revised child plan and directive acknowledgements atomically, and reconstruct that exact child plan for uncertain new-tab recovery. If notes race the final SQLite reservation, reject the stale prompt and retry only planning without a Send. Revoked `/build` approval must also be checked atomically at reservation time, not merely before PI inference. Emergency `/pause` on an ancestor must stop its READY/RUNNING descendants from new Sends after the current in-flight response. PI gets up to 100,000 characters of the visible assistant answer, including its middle; Telegram still gets an abbreviated report. A one-turn PI DONE is valid when the owner's actual goal is satisfied; never force extra turns just to meet a test count. A separately approved /build route provides a ChatGPT prompt-level workspace-write path. Synthetic cross-Mission tests are not unattended production acceptance.
- An authenticated Telegram `/build` command can create a PI-managed workspace-write Mission only when the local operator has pinned `telegram-build-project` to the exact configured PI project path. The recorded scope must propagate to PI and ChatGPT on every turn, including HANDOFF. PI stays tool-free; ChatGPT must actually have connected execution tools. Read-only `/auto`, native `/agent` and legacy `/continue` never inherit this authorization. Local approval revocation prevents subsequent sends; this is browser prompt authority, not an OS-enforced sandbox. For cross-Mission first-new-tab sends, recheck the exact parent visible prompt/answer SHA again immediately before SQLite reservation, after any asynchronous PI preflight; refuse a changed parent without Send. Do not assert Git or deployed effects without real readback.
- Node.js LTS (24+), `npm ci`, `npm run check`, `npm test`, `npm run build`.
- Browser-first default: no native coding-agent SDK or vendor selection is required. Native executors are operator-installed, in-process trusted plugins; each native Mission is pinned to one installed executor identity. All vendor-specific authentication, sandbox, proxies and SDK logic belong outside `src/core` and `src/plugins/telegram.ts`.
- Existing human ChatGPT conversation adoption is distinct from a Relay Send. Its stable user/answer hashes are a zero-turn checkpoint. PI's next reply must be grounded in that checkpoint; do not infer any browser Send from an adoption event. Playwriter tab groups are cosmetic; the optional browser watcher is deliberately profile-scoped (not group-scoped), baselines historical tabs on enable, and discovers only new/changed Playwriter-enabled ChatGPT dialogs. Do not claim control of unenabled Chrome tabs or silently adopt other websites. Watch revocation stops future dispatches; never replay ambiguous sends.
- Test with scripted fake executors; real Codex use is opt-in and requires an authorized account.
- Browser tests use a synthetic page unless the operator explicitly enables the Playwriter extension. Never run a real ChatGPT browser-send in CI or against an arbitrary open tab.
- Never run integration tests against a production repo or publish/restart services as a side effect.
- Update architecture/operations docs for protocol or state changes. Run `git status` and secret checks before public push.
- Read `STATE.md` before continuing implementation; it separates tested features from planned ones and tracks the current live-Codex blocker.
